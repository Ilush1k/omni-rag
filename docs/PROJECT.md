# Архитектура и вклад

Проект продолжает [Nionk/omni-rag](https://github.com/Nionk/omni-rag) и сохраняет исходную историю. Основа этой версии — ветка `feature/rag-memory-graph`, коммит [`a2c3c329`](https://github.com/Nionk/omni-rag/commit/a2c3c3295e04725dd010be40c3f27481f08759ea), где автором указан Ilush1k.

В этом коммите добавлены ограниченный обход графа, хранение summary в Redis/PostgreSQL, суммаризация, связи между чанками при индексации и интеграция этих функций в интерфейс. Остальная система использует код общего исходного проекта. Это командная работа, а не заявление об индивидуальном авторстве всей системы.

## Поток данных

1. `DocumentRouter` выбирает парсер по типу файла или URL.
2. CLI индексации проверяет хэши файлов, обрабатывает изменения и поддерживает очередь неудачных документов.
3. `VectorIndexer` разбивает текст, добавляет метаданные и связи чанков и отправляет плотные/разреженные представления в Qdrant.
4. Гибридный retriever получает кандидатов; `QdrantGraphTraverser` добавляет ограниченное число соседей через BFS.
5. Cross-Encoder сужает контекст до Top-4; локальная модель Ollama формирует ответ.
6. `DialogueSummarizer` обновляет summary, Redis хранит горячую копию с TTL, PostgreSQL — архив по пользователю/сеансу.

Qdrant хранит ребра в payload; сам обход выполняет Python-код. Это не отдельная графовая СУБД. Суммаризация в текущем Streamlit-сценарии вызывается последовательно после ответа.

Идентификатор пользователя в интерфейсе — средство выбора памяти, а не полноценная аутентификация. Для общего корпоративного развёртывания потребуются отдельные механизмы доступа и изоляции.
